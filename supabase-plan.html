方案 B：Supabase 雲端後端 改建置規劃

當客戶僅能使用共享虛擬主機（無法執行 Node.js 後端）時，改以「前台靜態＋Supabase 雲端後端」架構，確保後台管理系統完整運作。前台設計完全不變，僅資料來源改接雲端。

11資料表對應
14+API 對應項目
US$0初期月費（免費版）
2 階段遷移路徑

01決策背景與架構

觸發條件客戶確認僅能使用共享虛擬主機（cPanel／Plesk 網頁空間，僅 PHP＋MySQL，無法安裝 Node.js／PM2）
核心問題後台管理需要伺服器端 API 與資料庫讀寫，共享主機無法運行 Express 後端
本方案作法前台網站（純 HTML/JS/CSS）放共享主機；後台管理＋資料庫改用 Supabase（雲端 PostgreSQL＋Auth＋REST API）
前台設計完全不變：沿用原設計系統（色彩／字型／LOGO／影片／導覽），僅資料來源改為 Supabase
使用者瀏覽器
  • 前台（共享主機，靜態 HTML/JS/CSS）— supabase-js 僅讀取公開資料（anon key＋RLS）
  • 後台（共享主機，管理介面網頁）— Auth 登入 → CRUD 寫入（authenticated 角色＋RLS）
↓
Supabase 雲端
  • PostgreSQL（資料庫）· Auth（登入認證）· REST API（讀寫）· Storage（圖片／檔案）

02資料表對應（11 表 → Supabase）

欄位結構與規劃書一致，型態由 SQLite 對應至 PostgreSQL；可於 Supabase 管理介面（SQL Editor）直接建表。

規劃書資料表Supabase 對應主要欄位存取權限（RLS）
users改用 Supabase Auth（auth.users）＋ profiles 表存角色Email／密碼內建；profiles：id、role(admin/editor)僅 admin 可寫
brandbrand（單列）id、name、en、slogan、phone、email、addr、hours、affil、line公開讀admin 寫
herohero（單列）eyebrow、sub、title、intro公開讀admin 寫
prod_introprod_intro（單列）text公開讀admin 寫
groupsgroupsid、label、sort_order公開讀admin 全權限
categoriescategoriesid、group_id(FK)、name、sec、sort_order公開讀admin 全權限
itemsitemsid、category_id(FK)、model、brand、desc、sort_order公開讀admin 全權限
servicesservicesid、no、title、desc、sort_order公開讀admin 全權限
postspostsid、date、title、body、published(bool)、created_at公開僅讀已發布admin 全權限
pagespagesid、key(unique)、title、body公開讀admin 寫
activity_logactivity_logid、user_id(FK)、action、target、detail、created_at僅 admin 讀
RLS 核心防護：前台使用公開金鑰（anon key）僅能 SELECT 公開資料；寫入操作需登入且符合角色規則，即使金鑰外流也無法竄改資料。

03後台 API 對應（Express 路由 → Supabase）

規劃書第 7 節的 REST API 全部由 Supabase SDK／REST 介面取代，無需自建伺服器。

規劃書 Express 路由Supabase 對應操作（supabase-js v2）備註
POST /api/auth/loginsignInWithPassword({ email, password })取代 Session
POST /api/auth/logoutsignOut()—
GET /api/meauth.getUser()目前登入者
GET /api/site多表查詢；建議建 view_site 聚合前台聚合
GET /api/postsfrom('posts').select().eq('published',true).order('date')僅已發布
PUT /api/admin/brandfrom('brand').update({...}).eq('id',1)單列
PUT /api/admin/herofrom('hero').update({...}).eq('id',1)單列
PUT /api/admin/prod-introfrom('prod_intro').update({...}).eq('id',1)單列
…/groups、categories、items、services、posts CRUDfrom('表').select()/insert()/update().eq('id')/delete().eq('id')各模組 CRUD
PUT /api/admin/pages/:keyfrom('pages').update({...}).eq('key', key)資訊頁
GET /api/admin/activity-logfrom('activity_log').select().order('created_at', desc)稽核

04前台資料讀取對應

前台頁面原資料來源Supabase 對應
首頁/api/sitehero／brand／services／groups 查詢＋intro.mp4 放共享主機或 Storage
產品群組頁/api/sitefrom('groups').select('*, categories(*, items(*))').eq('id', id)
產品搜尋/api/sitefrom('items').select().ilike('model', %q%).or(...)＋分類篩選
最新消息/api/postsfrom('posts').select().eq('published',true).order('date', desc)
資訊頁／聯絡/api/sitefrom('pages').select().eq('key', key)
前台使用 anon key（公開金鑰）；因 RLS 僅開放 SELECT 公開資料，金鑰外流也無法寫入。

06遷移路徑（兩階段）

階段 A：資料遷移（SQLite → Supabase）

  • 建立 Supabase 專案建議區域：新加坡或東京（台灣延遲低）
  • SQL Editor 建表＋RLS11 張表＋profiles＋view_site＋Policies
  • 匯入 Seed 資料7 群組／94 分類／55 產品／4 服務／3 消息／3 頁面／品牌／hero
  • 匯入方式① 管理介面 CSV 匯入；② 一次性 Node 腳本寫入
  • 驗證筆數逐表 COUNT 比對原資料一致

階段 B：程式改接

  • 前台改接fetch('/api/site') → supabase-js 查詢（anon key）
  • 後台 SPAPreact 管理介面（登入＋各模組 CRUD＋儀表板）
  • 上傳共享主機前台與後台皆為靜態檔，無需 Node 執行環境
  • 移除自建後端依賴Express／SQLite／PM2 不再需要
  • 驗收對照規劃書第 12 節逐項測試
反向遷移亦可行：pg_dump 匯出資料 → 匯入自有 PostgreSQL → 前台改回自家 API；資料為標準 PostgreSQL，無綁定。

09決定流程

客戶主機類型確認 → 可用 VPS？ → 維持方案 A（Node/Express）
僅有共享虛擬主機？ → 採用本方案 B（Supabase）

確認清單：共享主機確認／是否已租（零新增費用）／同意資料存放雲端／正式域名與上傳方式／後台管理員 Email（1–2 名）。
